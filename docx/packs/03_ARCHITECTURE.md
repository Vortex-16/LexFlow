# System Architecture

## 1. Architectural shape

Use a modular application with a thin UI layer and explicit server-side domain boundaries.

```text
Browser
  |
  v
Next.js UI
  |
  +--> API / Server Actions
          |
          +--> Input Validation
          |
          +--> Request Classifier
          |
          +--> Retrieval Service
          |      |
          |      +--> Source connectors
          |      +--> User document index
          |
          +--> Legal Safety Rules
          |
          +--> LLM Orchestrator
          |      |
          |      +--> Prompt templates
          |      +--> Structured output parser
          |      +--> Citation verifier
          |
          +--> Document Service
          |      |
          |      +--> file validation
          |      +--> text extraction
          |      +--> section detection
          |      +--> chunking
          |
          +--> Audit / Metrics

Data layer:
- relational metadata
- vector index
- temporary/controlled document storage
```

## 2. Major modules

### `domain`
Pure business concepts and rules. No framework code.

### `application`
Use cases and orchestration. Coordinates domain services.

### `infrastructure`
LLM providers, vector store, source fetchers, file parsers, persistence.

### `ui`
React components, forms, views, accessibility, loading/error states.

## 3. Request lifecycle

```text
Input
 -> validate
 -> sanitize
 -> classify
 -> collect missing context
 -> retrieve
 -> rank evidence
 -> generate structured answer
 -> validate schema
 -> verify citations
 -> apply safety rules
 -> render
```

## 4. Citation validation

A response is not complete when the LLM returns text. The application must check that each substantive citation maps to retrieved evidence.

Suggested representation:

```ts
type Citation = {
  sourceId: string;
  title: string;
  locator?: string;
  quote?: string;
};
```

Do not trust citation IDs generated by the model without server-side verification.

## 5. Retrieval policy

Use a hybrid approach where practical:

- metadata filters first,
- lexical search for exact legal terms,
- semantic retrieval for natural-language intent,
- reranking for relevance,
- source authority weighting,
- deduplication.

For legal questions, source authority and jurisdiction fit are more important than raw semantic similarity.

## 6. Source hierarchy

Prefer, in order:

1. official legislation/regulations and official government sources,
2. official courts/tribunals or authoritative case databases where applicable,
3. recognized legal institutions or primary-source repositories,
4. carefully selected secondary explanatory sources.

The source hierarchy should be configurable by jurisdiction.

## 7. LLM boundary

The model may:

- summarize retrieved evidence,
- explain terminology,
- compare retrieved clauses,
- identify uncertainty,
- propose questions for further review.

The model must not be the sole authority for:

- determining the governing law,
- asserting current legal status without a source,
- fabricating citations,
- making unsupported outcome predictions.

## 8. Failure modes

### No evidence
Return a bounded response explaining that the system could not verify the claim.

### Ambiguous jurisdiction
Ask for jurisdiction before making jurisdiction-specific claims.

### Stale source
Show the source date and warn when the date may affect validity.

### Parser failure
Keep the original file private, report extraction failure, and offer a safe retry route.

### Provider outage
Return a controlled error with no internal details or secrets.
