# Demo + Submission Plan

## 1. The demo story

The demo should prove usefulness, not list features.

### Scene 1 — Ask

Ask a realistic plain-language question.

Show:

- concise answer,
- jurisdiction/context,
- source citation,
- expandable evidence,
- uncertainty where relevant.

### Scene 2 — Document

Upload a small synthetic agreement.

Ask:

“What does the termination clause allow?”

Show the answer and jump directly to the clause/page.

### Scene 3 — Compare

Upload version A and version B.

Show:

- changed section,
- what changed,
- why the difference matters,
- exact evidence from both versions.

### Scene 4 — Safety

Ask a question that lacks jurisdiction or sufficient evidence.

Show that the assistant does not bluff; it asks for the missing context or explains the evidence limit.

## 2. README content

The final README should contain:

- project name
- one-paragraph problem statement
- chosen vertical/persona
- key capabilities
- architecture diagram or concise architecture explanation
- setup instructions
- environment variables
- safety/grounding approach
- testing approach
- screenshots/GIF only if they materially help and keep repo size controlled
- assumptions
- limitations
- repository size note

## 3. Submission checklist

- GitHub repository is public.
- Only one branch exists in the submission repository.
- Repository remains below 10 MB.
- README is complete.
- No secrets or local artifacts.
- Main build/test workflow passes.
- Demo path can be completed quickly.
- Error and safety states are demonstrable.

## 4. Three-attempt strategy

Because only three attempts are available, do not spend an attempt on incomplete polish.

### Attempt 1
Functional baseline + clean repository + tests + README.

### Attempt 2
Target gaps in code quality, security, testing, accessibility, and alignment.

### Attempt 3
Final regression pass and presentation polish only after all hard gates pass.
